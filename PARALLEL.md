# Как втроём вайбкодить в одном репозитории

Главная опасность дня — не баги, а потерянный код. Три агента параллельно правят одни
и те же файлы, кто-то делает `push --force`, и полчаса работы исчезают. Ниже то, что
надо сделать, чтобы этого не случилось. Пять минут на чтение окупаются с запасом.

---

## Правило первых пяти минут: разделите файлы, а не задачи

Задачи неизбежно пересекаются, файлы — нет. Договоритесь так, чтобы у каждого пилота
были **свои файлы**, в которые больше никто не пишет. Тогда мержить будет почти нечего.

Рабочая раскладка на троих:

```
index.html        — пилот 1 (разметка, каркас)
src/core.js       — пилот 1 (основной сценарий продукта)
src/content.js    — пилот 2 (тексты, данные, копирайт)
src/style.css     — пилот 2 (оформление)
src/wow.js        — пилот 3 (генерация голоса/картинок/видео)
src/easter.js     — пилот 3 (пасхалка)
```

Файлов может быть больше, суть одна: **один файл — один хозяин**. Запишите раскладку
в `AGENTS.md`, чтобы её видели все агенты.

Если нужна правка в чужом файле — не лезьте туда сами, скажите хозяину. Тридцать секунд
разговора дешевле конфликта.

Каждому пилоту стоит начать сессию так:

```
Ты отвечаешь только за файлы src/wow.js и src/easter.js. Другие файлы не редактируй.
Если для задачи нужно изменение в чужом файле — не делай его, скажи мне, я передам владельцу.
```

## Как двигаться: все в main, ветки не нужны

Для двух часов и трёх человек ветки с пул-реквестами только жгут время. Работает
проще: все коммитят в `main`, а перед каждым пушем подтягивают чужое.

Цикл, который повторяется каждые 10–15 минут:

```bash
git add -A && git commit -m "что сделал" && git pull --rebase && git push
```

Именно в таком порядке: сначала коммит, потом `pull --rebase`, потом `push`.
Если пушить раз в час, конфликт будет огромным и разгребать его придётся вручную.

**Коммитьте перед каждым большим промптом.** Агент, ушедший переписывать пол-продукта,
переживается спокойно, когда есть точка возврата.

### Что делать с конфликтом

Если зоны разделены, конфликты будут редко и мелко. Когда всё же случился:

```bash
git status
```

Git покажет файлы с конфликтом. Открывайте, оставляйте нужное, убирайте маркеры
`<<<<<<<`, `=======`, `>>>>>>>`, дальше:

```bash
git add . && git rebase --continue
```

Совсем запутались — не геройствуйте:

```bash
git rebase --abort
```

Вы вернётесь к своему состоянию, ничего не потеряв, и попробуете ещё раз.

### Чего не делать никогда

- **`git push --force`** — это то самое, чем стирают чужую работу. Если агент предлагает
  форс-пуш, откажитесь и позовите владельца `main`
- **`git reset --hard`** без разговора с командой
- Не коммитьте `.env`. Хук уже стоит, но `--no-verify` его обходит — не обходите

## Владелец main

Назначьте одного человека (обычно это пилот с подпиской Max), который следит за тем,
что в `main` лежит рабочая версия. Его задача одна: если после чьего-то пуша демо
перестало открываться, откатить и сказать вслух.

```bash
git log --oneline -10        # найти последний нормальный коммит
git revert <хеш>             # откатить сломавший, историю не переписывая
```

`revert` безопаснее `reset`: он не переписывает историю и не ломает работу остальным.

## Два агента на одном ноутбуке

Иногда у одного человека подписка Max, а строить хочется в два потока. Не запускайте
две сессии в одной папке — они будут перетирать файлы друг друга. Сделайте вторую
рабочую копию:

```bash
git worktree add ../__TEAM__-wow
```

Появится соседняя папка со своей веткой, там запускаете второго `claude`. Пуш и мерж
как обычно. Когда закончили:

```bash
git worktree remove ../__TEAM__-wow
```

## Роли без подписки

Вайбкодят двое-трое, а в команде девять человек. Остальным есть чем заняться, и это
не «посидеть рядом»:

- **Тестировщики** держат открытым демо на телефоне и жмут всё подряд после каждого
  деплоя. Баг, найденный за минуту, стоит дешевле бага, найденного диверсантом
- **Писатели промптов** формулируют задачи текстом, пока пилот занят. Готовый абзац
  вставить быстрее, чем придумать на ходу
- **Контентщики** пишут тексты, собирают картинки, придумывают названия — всё это
  потом просто вставляется в `src/content.js`
- **Питчер** с первой минуты собирает демо-сценарий: что показываем, в каком порядке,
  на чём делаем паузу. Три минуты на сцене нужно отрепетировать хотя бы раз
- **Заказчик** принимает фичи и говорит «беру» или «переделать»

## Если всё-таки потеряли код

Всё, что было запушено, лежит на GitHub — идите на страницу репозитория и смотрите
историю коммитов. Локально помогает:

```bash
git reflog
```

Это список всех состояний, включая те, что «пропали». Находите нужный хеш и
`git checkout <хеш>`. Потерять по-настоящему можно только то, что ни разу не коммитили —
поэтому коммитьте часто.
